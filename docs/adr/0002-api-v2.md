# 2. API v2: a schema, jobs and events, one settings object

- **Status:** accepted — shipped in 2.1.0; v1 kept alongside for that release
- **Decided in:** roadmap Phase 1 ([roadmap.md](../roadmap.md))

## Context

The 2.0 server had one client, the web UI, and an API shaped around it:

- `POST /api/convert` took **eleven mandatory multipart fields**, one per
  setting; leaving one out was a 400. Every default lived in the client —
  three times in `api.js` and once more in `App.jsx` — so adding a setting
  meant editing four places in the frontend and the backend besides.
- **Progress was polled** every 800 ms; nothing could be cancelled; there was
  no job list; jobs and their files were never cleaned up.
- The **preview** ran the whole pipeline a second time through a copy of it,
  wrote a `.litematic` to disk and read it back.
- It **listened on every interface** with no authentication, fine for a
  local tool until a game process starts it for you.

The roadmap adds a second client, the Minecraft mod, written in another
language, which must show the same settings with the same labels, defaults
and ranges, start the server itself, and follow conversions — and the CLI
builds the same settings from flags. A shape that made each client restate
every setting would have drifted at once.

## Decision

A second API version, mounted beside the first:

- **The server describes its settings.** `GET /api/schema` lists every field
  — type, range, slider range, step, unit, default, group, label, help,
  visibility condition — plus the Minecraft versions and formats it can
  write. It is generated from the one `Settings` definition in
  `schemgen-core`, and a test fails if the two disagree. The web UI and the
  mod draw their forms from it and hard-code no field.
- **One settings object.** `POST /api/jobs` takes model files and a single
  `settings` JSON object; every key is optional, and keys the server does not
  know are reported back rather than silently dropped. The CLI's flags build
  the same object.
- **Jobs are resources.** `GET`/`DELETE /api/jobs/{id}` (delete cancels a
  running job), `GET /api/jobs`, and server-sent events on
  `/api/jobs/{id}/events`, with polling as the fallback. Downloads,
  thumbnails, save and reveal hang off the job. Finished jobs and their files
  are forgotten after `--job-ttl`.
- **The preview is the pipeline without a writer.** `POST /api/preview`
  returns the blocks packed (base64 of little-endian `Int32` quadruples) and
  stops working when the client disconnects.
- **Safe to launch from a game.** Binds `127.0.0.1`; checks `Host` against
  DNS rebinding and `Origin` against cross-site posts; an optional bearer
  token (`--token`, `SCHEMGEN_TOKEN` — which never appears on a command line —
  or `--token-file`). For launchers: `--port 0` prints `listening <url>`,
  `--exit-with-stdin` ties the server's life to its parent.
- `GET /api/health` says `"api": 2`; a client checks it before anything else.

v1 stays mounted for one release, running on the same jobs, so scripts
written against it keep working while they move.

## Consequences

- Adding a setting is a change to `settings.rs` and `schema.rs` (and its row
  in [design.md](../design.md)); the web UI, the mod and the HTTP API pick it
  up with no change of their own ([web.md](../web.md#adding-a-setting)).
- The mod needs a 2.1 server; it says so plainly when it finds an older one.
- Live progress without polling, cancellation, and a server that cleans up
  after itself.
- A server a game process can start on a free port with a fresh token, which
  the mod's sidecar does ([mod.md](../mod.md)).
- Two APIs to keep working for a release. **Next release:** remove v1.

## Alternatives considered

- **Keep flat multipart fields and add the new routes:** every client would
  still restate every setting, and the mod would have to be updated in step
  with the server for each new field.
- **WebSockets or gRPC for progress:** more machinery on both ends for a
  one-way stream. Server-sent events work in every browser, through
  `java.net.http`, and degrade to polling when a proxy breaks the stream.
- **Share a settings definition as code** (generated TypeScript and Java):
  a build step in three toolchains, and a client built against one server
  version would still misdescribe another. Asking the running server is
  always right.
