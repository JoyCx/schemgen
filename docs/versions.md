# Minecraft versions

A schematic is made *for* a Minecraft version — its **target**. The target
decides two numbers stamped into the file.

## What the numbers mean

**`MinecraftDataVersion`** is the game version the file claims to come from.
When Litematica loads a schematic stamped *older* than the running game, it
upgrades the block palette through Minecraft's DataFixer; one stamped more
than a few releases *newer* than the game gets a warning. It is the number
that has to be right.

**Litematica's schematic `Version`** is the file format's own version:

| Litematica for | Writes | Reads |
|---|---|---|
| 1.18.x, 1.19.x, 1.20.x | `Version` 6 | 1–6 |
| 1.21.x and the builds for 26.x | `Version` 7 | 1–7 |

(Checked against `LitematicaSchematic.java` in maruohon's 1.18–1.20 branches and
sakura-ryoko's 1.21–26.x ones.) Version 7 only changed how sleeping entities'
positions are stored, and block-only schematics read identically under both,
so 6 would load everywhere from 1.18 on. SchemGen2 writes 7 for targets from
1.21 anyway, because that is what Litematica itself writes there.

## Targets

| Target | Data version | Litematica `Version` |
|---|---|---|
| 1.16.5 | 2586 | 6 |
| 1.17.1 | 2730 | 6 |
| 1.18.2 | 2975 | 6 |
| 1.19.4 | 3337 | 6 |
| 1.20.1 | 3465 | 6 |
| 1.20.4 | 3700 | 6 |
| 1.20.6 | 3839 | 6 |
| 1.21.1 | 3955 | 7 |
| 1.21.4 | 4189 | 7 |
| 1.21.5 | 4325 | 7 |
| **1.21.8** | **4440** (default) | 7 |
| 1.21.10 | 4556 | 7 |
| 1.21.11 | 4671 | 7 |
| 26.1 | 4786 | 7 |
| 26.2 | 4903 | 7 |
| 26.3 | 5023 | 7 |

Data versions are from PrismarineJS `minecraft-data`
(`data/pc/common/protocolVersions.json`). Mojang retired `1.x` numbering after
1.21.11; 26.1 is its successor. `schemgen2 targets` prints the table the binary
was built with.

Pick the version you play. A schematic for 1.21.4 loads in 1.21.4 and every
later version; one for 1.21.8 may warn in 1.21.4.

**Floor:** 1.16.5 — post-flattening block names, and the oldest version
Litematica is still meaningfully used on. Pre-1.13 numeric block IDs are out of
scope. **Ceiling:** the newest row.

For a version without a row, `--data-version <N>` (or a bare number as the
`target` setting) stamps any data version from 1.16.5's on. A number that
belongs to a named target *is* that target.

## Choosing a target

| Where | How |
|---|---|
| CLI | `schemgen2 convert model.glb --target 1.20.4` |
| API | `"target": "1.20.4"` in the `settings` JSON — see [api.md](api.md) |
| Web UI | The *Minecraft* dropdown, remembered per machine. Picking a folder inside a launcher instance sets it to that instance's version. |
| Server default | `schemgen2 serve --target 1.20.4`, or `SCHEMGEN_DATA_VERSION` |

The web UI's folder suggestions read the game version from each launcher
instance — Prism Launcher and MultiMC's `mmc-pack.json`, CurseForge's
`minecraftinstance.json`, older Modrinth App profiles' `profile.json` — and map
it to the newest target not newer than it (`1.20.2` → `1.20.1`).

## Blocks per version

A target only gets blocks that exist in its version, so a schematic never
contains a name its game does not know — an unknown block would load as air.
`backend/data/block_versions.json` records, for every palette block, the data
version of the first target it exists in:

| From | Blocks added to the palette |
|---|---|
| 1.16.5 | 137 — the floor |
| 1.17.1 | 25 — deepslate, tuff, calcite, dripstone, amethyst, copper, raw ore blocks |
| 1.19.4 | 8 — mud bricks, packed mud, muddy mangrove roots, froglights, sculk, reinforced deepslate |
| 1.21.1 | 8 — polished tuff, tuff bricks, chiseled tuff, chiseled copper |
| 1.21.4 | 3 — resin block, resin bricks, chiseled resin bricks |

The table is generated by [`tools/gen_block_versions.py`](../tools/gen_block_versions.py)
from each target's block list in PrismarineJS minecraft-data. Blocks a release
only offered behind an experimental feature flag count from the release that
enabled them: the tuff and chiseled-copper blocks are in 1.20.3–1.20.6's
registry, but only a world with the *Update 1.21* experiment can place them.
Versions minecraft-data has no block list for yet (26.2, 26.3 at the time of
writing) inherit the newest list it has. The generator stops with an error if a
palette block ever disappears from a later version — the sign of a rename that
needs a decision.

`schemgen2 palette --target 1.17.1`, `GET /api/palette?target=1.17.1` and the
`blocks` count of each entry of `GET /api/schema`'s `targets` show a target's
palette. A block missing from the table (say, after rebuilding the color table
from a newer resource pack) is only used for the newest target until the table
is regenerated.

## File formats

The target stamps every format the same way.

| Format | `format` | For | Notes |
|---|---|---|---|
| `.litematic` | `litematic` | Litematica | Default. Litematica `Version` 6 or 7 as above. |
| `.schem` Sponge v2 | `schem` | WorldEdit 7.x, FAWE; Litematica imports it | Reads in every WorldEdit 7 release |
| `.schem` Sponge v3 | `schem-v3` | WorldEdit 7.3+ | What newer WorldEdit writes itself |
| `.nbt` structure | `nbt` | Structure blocks, `/place template` | Air is left out, so placing keeps what was there; structure blocks load at most 48 × 48 × 48 |

Choose it with `--format` on the CLI or `"format"` in the API settings.

## Testing

Three layers, from fastest to closest to the game:

1. **Unit tests** (`cargo test`): every writer is read back with SchemGen2's own
   NBT reader and checked cell by cell; the palette tests check that each
   target's palette only grows with the version and never includes a block
   newer than it.
2. **Independent readers** ([`tools/check_outputs.py`](../tools/check_outputs.py),
   run in CI): converts a model for every target × format with the real
   binary, then reads each file with litemapy and nbtlib — code SchemGen2 did
   not write — and checks the stamped versions, the block count, and that
   every block exists in that version's minecraft-data block list.

   ```bash
   pip install litemapy nbtlib
   python tools/check_outputs.py --binary backend/target/release/schemgen2
   # 64/64 files passed
   ```

3. **In game** (manual, before a release): one Prism Launcher instance per
   target with Litematica (and WorldEdit for `.schem`), each loading the same
   conversion of `backend/fixtures/metal_transforms.glb`:

   | Check | How |
   |---|---|
   | Loads without warnings | Litematica: *Load Schematics* → the file |
   | No missing blocks | Place it; no air holes where blocks should be |
   | Right size | Litematica's *Schematic info* matches `grid` from `--json` |
   | `.schem` | `//schem load <name>` then `//paste` |
   | `.nbt` (≤ 48³) | Structure block in *Load* mode, or `/place template` |

   Screenshot each and keep them with the release notes.

## Adding a version

1. Look up its data version in minecraft-data's `protocolVersions.json`.
2. Add a row to `TARGETS` in `backend/crates/core/src/targets.rs` (the
   Litematica version follows from the data version) and to the table above.
3. `python tools/gen_block_versions.py` — regenerates the block table, and
   fails if a palette block was renamed or removed.
4. `python tools/check_outputs.py --binary …` — every format for the new
   target, checked against its block list.
